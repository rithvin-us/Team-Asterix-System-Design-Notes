# Requirements

> **Status:** stub

What the system must do, and how well.

## To write up here

- Functional: what it must do. Phrasing, granularity, how many is too many
- Non-functional: how well. Latency, weight, cost, power budget, reliability, safety, throughput
- Turning adjectives into numbers — the highest-value habit in this whole area
- Measurability: stating how a target will be verified, not only the target
- Requirements that sit in a list nobody used
- Where requirements come from when nobody hands you any
- Conflicting requirements as the source of every interesting trade-off

## Guiding questions

- What must it do? List them plainly.
- For each target: what number, measured how, and what happens if you miss it?
- Which two of your requirements are in tension with each other?
- Can you point at the part of the design that exists because of each requirement?
